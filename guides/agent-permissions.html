Lesson 02 / Governance

Setting permission boundaries for AI agents

An operating guide to observing, proposing and acting permissions, human approvals, audit logs and safe escalation.

Separate information access from operational authority

A useful agent does not require unrestricted access to every account or application. Start by listing the information the workflow requires and the actions the business expects the agent to perform. Treat reading a document, drafting an email and sending that email as three distinct capabilities. Assign only the privileges required for the current task.

Keep the agent's working identity separate from an administrator identity. Where the platform supports scoped permissions, provide read-only access by default. Do not store access tokens in source code, analytics reports or public repositories. Use an approved secret manager and rotate credentials when roles or integrations change.

Use three operating levels

Observe. Read permitted data and return findings or questions. The agent has no external write authority. Suitable tasks include comparing public specifications or summarizing material in an authorized folder.

Propose. Prepare a draft, a change request or a payment recommendation for a human decision. Preserve the proposed content, affected records and reasons for the action.

Act. Perform a narrowly defined write action after appropriate authorization. Limit the permitted target, transaction type and maximum scope. Record who approved the action and whether the external system accepted it.

Design review gates around consequences

Review should focus on potential harm, not solely the size of an action. A small automatic purchase affects company funds. A single incorrectly addressed email exposes information. A code change in a production payment system affects customers even if the diff is short. Classify actions by reversibility, external impact, data sensitivity and financial exposure.

Require an explicit approval checkpoint for outgoing customer or recruiter messages, financial transactions, permissions changes, production deployments and deletion of customer records. The approval screen should show the destination, exact content or change, relevant evidence and the intended consequence. A generic approval checkbox without an understandable preview is insufficient for high-impact work.

Prepare for an unexpected instruction

Information from a webpage, inbox or repository might contain text instructing an agent to reveal credentials or change its task. Treat that material as data, not a higher-priority instruction. Restrict tool access by task, validate the destination of external messages and require human review when an untrusted source requests a privileged action.

Keep a log of the source materials consulted, proposed actions, approvals, external API results and errors. Protect logs from unnecessary personal data exposure and apply a defined retention schedule. Add an emergency stop that revokes task credentials and blocks new writes without damaging existing evidence.

Before granting additional access

  • Name the accountable business owner and the technical operator.
  • Specify permitted data sources, write targets and transaction limits.
  • Document the approval process, exception routing and credential handling.
  • Test failed API calls, duplicate events, missing records and malicious instructions in source material.
  • Verify the audit trail and a manual recovery process.

Expand permissions only after the measured error rate, quality and audit controls support the change. Increased task volume alone is not evidence that broader privileges are appropriate.
